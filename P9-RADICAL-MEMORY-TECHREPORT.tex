\author{Technical engineering report}
\date{11 August 2026}

\begin{abstract}
Long hint-guided Prover9 searches in algebra can retain millions of clauses in
the set of support (SOS), millions of demodulators, millions of disabled proof
ancestors, and hundreds of thousands of hints.  Historical runs reported
18.8\,GiB for an Osborn proof and 125.8\,GiB for an AAPERM prefix.  The initial
hypothesis that disabled clauses alone caused this growth was only partly
correct.  Clauses rejected immediately as tautologies or by forward
subsumption were not retained, while deleting almost all disabled clauses saved
only 22\% at the 4000-given Osborn boundary.  The dominant architectural
problem was that retained but not yet selected SOS clauses remained represented
as many separately allocated clause, literal, term, and index objects connected
by C pointers.  They also remained in the indexes used for immediate
simplification, so one passive clause could consume memory through several
representations.

This report describes two responses.  The first is a DISCOUNT-style loop with a
strict active/passive separation.  A passive clause and a hint are stored in
compressed form with only small selection or status records in RAM.  Work that
would generate many paramodulation or hyperresolution conclusions is described
by a small resumable record, while only a bounded number of conclusions exist
as ordinary clauses at once.  This Waldmeister-inspired design gives the best
bound on how RAM grows with the search, but changes when simplification and
generating inferences occur.  On the supplied Osborn hint chains, matching more
hints did not reproduce the historical proof: demodulation and inference timing
are part of the effective search strategy.

The accepted response is an eager compact OTTER-compatible loop.  It preserves
the old treatment of every retained clause for demodulation, unit conflict,
subsumption, backward demodulation, hint matching, and given-clause selection.
An archived passive clause is kept in an append-only disk file with a small selection
record in RAM.  Four smaller indexes refer to clause numbers rather than to
pointers and cover rewriting, unit operations, backward demodulation, and
nonunit subsumption.  An ordinary clause is reconstructed only for an exact
logical test or when selected.  The established matcher, unifier, rewriter, or
subsumption test still makes every final decision.

On the accepted full proof, old P9 used 550,400\kib peak RSS and 765.69 seconds
of user CPU.  Compact OTTER proved at the same 2945-given boundary, with the
same 7051 proof clauses and 3231 new hints, in 754.78 user seconds and
127,420\kib peak RSS.  This is a measured 76.85\% whole-process reduction
(4.32 times smaller) with 1.42\% less user CPU.  Memory counters captured at
termination explain 96.93\% of process memory after shared pages are
apportioned among their users.  A larger 11,000-given comparison now includes
ordinary Prover9, the early compact implementation, and the current file-backed
implementation.  The current compact run lowered its terminal peak-RSS
diagnostic from 3,603,800 to 834,780\kib (76.84\%, or 4.32 times smaller), but
used 12,201.61 rather than 5,110.38 user seconds (2.388 times the CPU).  It is
19.43\% faster than the early compact run, yet still performs 19.190 billion
unit-conflict exact tests and examines 21.500 billion backward-demodulation
posting groups.  Thus the no-CPU-penalty result applies only to the
2945-given acceptance proof.  The large run also had allocator compact policy
disabled, so a controlled allocator and cgroup rerun remains necessary for a
total-job memory claim; its CPU diagnosis is already decisive.
\end{abstract}

\section{Terminology and scope}

The report uses the standard saturation terminology familiar from OTTER,
Prover9, E, Vampire, the \emph{Handbook of Automated Reasoning}, and Harrison's
\emph{Handbook of Practical Logic and Automated Reasoning}.

The \emph{passive set}, called \setting{sos} by Prover9, contains retained
clauses waiting to be selected.  The \emph{active set}, called
\setting{usable}, contains selected clauses available as parents of generating
inferences.  A \emph{given clause} is selected from passive, moved to active,
and combined with suitable active clauses by the enabled inference rules.
Generating inferences are called expansion; simplification and redundancy
elimination---demodulation, unit deletion, forward/backward subsumption, and
backward demodulation---are called contraction.

A hint is a clause used for search guidance, not an inference premise.  A
derived clause that subsumes a hint, is subsumed by a hint, or satisfies the
configured matching relation can receive favorable selection treatment.  This
is the hints/proof-sketch tradition developed by Veroff and implemented in
OTTER and Prover9.

With \emph{hint degradation}, each previous use of the same hint adds a weight
penalty to its next match.  This prevents one repeatedly matched hint from
dominating selection forever.

The main nonstandard terms describe representations.  They are defined here in
terms of their theorem-proving role:
\begin{itemize}
  \item \emph{Serialization} writes a clause as a compact sequence of numbers
        for symbols, variables, literals, attributes, and justification instead
        of retaining a network of C objects and pointers.  \emph{Materializing}
        a clause reconstructs those ordinary objects for an exact test.
  \item A \emph{stable clause number} is Prover9's ordinary clause ID used in
        an index instead of a memory address.  It remains valid after the body
        moves from RAM to the archive.
  \item A \emph{dense record} is one small fixed-size array entry.  Here it
        holds selection and status data, but no literals or terms.
  \item An \emph{index feature} is a cheap necessary property, such as literal
        sign, root symbol, or symbol at a short term position.  A \emph{posting
        list} is the list of clause or hint numbers having that feature.
        Intersecting lists keeps only numbers present in every list, because a
        possible answer must have every required feature.
  \item A \emph{conservative filter} may return extra, false candidates but
        never omit a possible answer.  The established matcher, unifier,
        subsumption test, or rewrite operation rejects the extras and makes the
        final decision.  The report sometimes calls this the authoritative test.
  \item FPA is Prover9's ordinary feature-path term indexing.  In the relevant
        implementation it retains live term objects and pointers.
  \item A \emph{cache} saves answers to recent index queries in a fixed-size
        table.  An \emph{epoch} is a version number used to detect that rewrite
        rules or hint state have changed since a clause was processed.
  \item A \emph{memory allocator} is the library code that obtains RAM for
        Prover9 and later reuses or returns freed blocks.  A \emph{priority
        queue} arranges waiting clauses so that the next-best one can be found
        without scanning the whole passive set.
  \item A \emph{radix-compressed path} stores several consecutive one-child
        discrimination-tree steps as one sequence.  A \emph{token} is a 32-bit
        number representing a symbol, variable, or boundary in a serialized
        term.  A \emph{shared term pool} stores one sequence per retained clause
        so that several indexes can refer to it instead of copying it.
  \item The \emph{inference frontier} is the work waiting between choosing
        inference parents and processing the resulting clauses.  It holds
        clauses in the ordinary mode and small resume records in collective
        mode.
  \item RSS counts a process's pages in physical memory; peak RSS is its
        high-water mark.  PSS divides a shared page among its users.  An mmap
        makes file pages part of the process address space, where accessed pages
        count in RSS.  Explicit reads copy only requested records, although the
        kernel may still cache recently read file blocks.
  \item A SHA-256 digest is a 64-hexadecimal-character identifier computed from
        a file or event log.  Equal digests verify byte-for-byte equality here;
        they do not replace checking the logical proof.
\end{itemize}

Accordingly, ``exact index'' below means that the final operation agrees with
the ordinary implementation.  The intermediate candidate set need not itself
be exact.

\section{The original memory problem}

The motivating searches in the supplied AIM problem collection are much larger
than their given counts suggest.
A few thousand selected clauses can generate and retain millions of SOS
clauses, and many of those retained equations can become simplifiers before
selection.

State & Given & SOS & Demodulators & Disabled & Hints \\

Osborn proof & 11,242 & 4,594,786 & 3,759,850 & 6,519,452 & 310,153 \\
AAPERM prefix & 12,560 & 8,504,637 & 6,199,295 & 4,593,127 & 220,117 \\

The corresponding internal \setting{Megabytes} values were 2626.98, 18810.85,
and 125829.01\mib.  The AAPERM profile further showed that inference generation
was not the dominant CPU term: about 902 of 225,533 user seconds were in
\setting{infer}; preprocessing, subsumption, indexing, disabling, and backward
demodulation dominated.  Most time was therefore spent simplifying clauses and
maintaining redundancy indexes, not applying generating inference rules.

\subsection{What the 2024 RAM discussion corrected}

The archived \setting{Plans-RAM-24.txt} discussion prevents two incorrect
interpretations.

First, \setting{Generated} is not a resident-clause count.  Immediate
tautologies and clauses rejected by forward subsumption are normally destroyed.
They consume CPU and create temporary objects, but their count does not explain
memory still occupied at the end of the run.

Second, disabled clauses matter, especially late in a long run, but are not the
whole problem.  Direct deletion experiments measured:

\begin{center}
\begin{tabular}{lrrr}
\toprule
Boundary & Ordinary & Delete disabled & Saving \\
\midrule
1000 givens, hints & 674\mib & 644\mib & 4.5\% \\
2000 givens, hints & 1101\mib & 963\mib & 12.5\% \\
4000 givens, hints & 2627\mib & 2037\mib & 22\% \\
8000 givens & 9192\mib & 6470\mib & 30\% \\
\bottomrule
\end{tabular}
\end{center}

At 4000 givens the disabled population fell from 577,347 to 383 while the
588,252-clause SOS and its eager indexes remained.  Moreover, proof
justifications refer to parent clause numbers.  Freeing a disabled object
without a replacement store leaves parent references that no longer lead to a
printable, checkable clause.  A radical solution therefore had to store proof
history compactly as well as changing the live SOS and its indexes.

\subsection{Logical bytes are not resident bytes}

Prover9's historical \setting{Megabytes} mostly counts memory requested through
its own allocator.  Memory obtained by the C library or by mapping a file can
be absent from that counter even while it occupies physical RAM.  Conversely,
the logical length of an archive file is a disk quantity, not resident RAM.
Measurements therefore distinguish Prover9's component counts, current RSS,
PSS (which apportions shared pages), and whole-run maximum RSS from
\setting{/usr/bin/time -v}.

This mattered in a long DISCOUNT run.  Its open but unlinked mapped file was
13,419,485,217 logical bytes and occupied 9.7\,GiB on disk, yet
10,223,128\kib of the mapping was also in physical memory.  Mapping a file is
not a promise that it stays out of RAM: reading a mapped page asks the operating
system to bring it into memory.  A former statistics routine read every record
and thereby made almost the whole file resident.  The accepted configuration
instead reads individual records into a small buffer.

The operating system can still retain recently read blocks in its filesystem
cache.  These blocks can be discarded under memory pressure and are absent from
process RSS/PSS, but may be charged to the Linux control group (cgroup)
containing the job.  Thus 127,420\kib is an exact process peak-RSS result, not
the maximum RAM used by both the process and cached archive data.  Total-job
claims require cgroup \setting{memory.current},
\setting{memory.peak}, and the \setting{file} fields of
\setting{memory.stat}.

\section{Semantic constraints}

A Prover9 SOS clause is passive for generating inferences but, in the
traditional OTTER loop, not passive for contraction.  A newly retained equation
can become a demodulator immediately, rewrite old SOS and usable clauses, rewrite
hints, and change later subsumption decisions.  Unit clauses participate in
unit conflict and simplification; nonunit clauses must remain visible to
subsumption.  Hint matching occurs while a candidate is an ordinary clause,
before it is added to the passive set, and affects its weight and selection
queue.

Four contracts follow.

\paragraph{Search.}
The mode intended to reproduce the old selected-clause sequence must execute
the same sequence of immediate
simplification and redundancy operations for a retained clause.  Selection
cycles, weights, hint degradation,
\setting{match_once}, matcher limits, and actions must observe the same result
in the same order.  Compact storage may change representation; it may not delay
the clause's use as a simplifier and silently turn OTTER into DISCOUNT.

\paragraph{Hints.}
Hints are not active inference premises, but equivalence handling, ordinary and
flipped matching, subsumption matching, degradation, matcher limits,
\setting{back_demod_hints}, and checkpoint state must remain exact.  An archived
passive is checked against hints while it is still an ordinary reconstructed
candidate.  It is archived only after the established exact hint routines have
run.

\paragraph{Proofs.}
Every parent must remain recoverable by clause number after its ordinary body
is freed.  The archive retains clause body, attributes, flags, matching-hint
state, and justification.  Damaged records must cause an explicit error rather
than appear in a proof.

\paragraph{Indexes.}
Removing a passive clause's literals and terms also invalidates pointers to
those objects in ordinary indexes.  Every operation that must see passive
clauses therefore needs a smaller clause-number-based index, or the ordinary
clause must remain in RAM.  Compact OTTER refuses to start unless all four
required replacements are active, preventing a partial mode from silently
omitting passive clauses from a logical operation.

\section{Waldmeister and the DISCOUNT/collective path}

Hillenbrand's Waldmeister account emphasizes three ideas.  First, consecutive
one-child steps in a discrimination tree can be stored together rather than as
pointer-heavy nodes.  Second, only active equations need participate in
inference and simplification indexes.  Third, the critical pairs belonging to
one newly active equation need not all be constructed immediately.  One small
record can describe the group, remember where generation should resume, and
store the least remaining weight; only a fixed number of promising pairs need
exist individually.  In Waldmeister's analysis this changes passive memory
from growth proportional to the square of the search length to growth
proportional to the search length.  Its reported unit-equational workload
represented more than 500 million passive equations with about 200 MB.

That number cannot be transferred directly to Prover9's paramodulation and
hyperresolution workloads.  The architectural question is nevertheless the
right one: represent delayed inference work rather than every conclusion.

\subsection{Strict active/passive ownership}

\setting{assign(search_loop,discount)} inserts only selected active clauses in
inference and simplification indexes.  A new candidate is simplified,
matched against hints, assigned its selection weight, and stored passively.  It
does not become an inference parent or demodulator until selection.  At that
point Prover9 checks whether the rewrite system has changed since the clause was
stored; if necessary it simplifies the clause again and returns the changed
form to passive or deletes it with a justification.

With \setting{assign(passive_store,dense)}, one small array record replaces a
full passive clause with separately allocated literals, terms, list entries,
and priority-queue nodes.  The record holds the clause number, weight, age,
semantic classification, matched hint, and values required by the selection
rules.  The complete clause and justification are stored in compressed form
and reconstructed at selection.

\subsection{Packed hints}

The old FPA hint index kept complete term trees in RAM.  The packed mode stores
each hint as a compact number sequence, plus small arrays for active, matched,
and degraded state.  Lists keyed by safe properties such as root symbol or a
short term path return hint numbers that might match; Prover9 reconstructs only
those hints and applies its established exact routines.  The first packed
implementation saved RAM but was too slow: at one 1000-given boundary it used
295,680\kib versus old P9's 507,108\kib, but took 441.39 instead of 113.44 CPU
seconds.  Its structural lookups returned billions of possible hints for exact
checking.

The successor \setting{packed_fast} made five concrete changes:
\begin{enumerate}
  \item it scans a short sparse list of hint numbers but uses a bitmap---one
        bit per possible hint number---for dense lists;
  \item it distinguishes queries by their complete required feature set rather
        than by a coarse summary that can confuse different queries;
  \item a fixed-size cache reuses a combined candidate list only while every
        relevant part of the hint index is unchanged;
  \item unit hints can be matched directly against their compact encoding,
        avoiding reconstruction of a term tree for that common case; and
  \item Prover9's special hint symbol \setting{_AnyConst}, which stands for an
        arbitrary constant during hint matching, is tracked separately without
        forcing every ordinary query to scan all such hints.
\end{enumerate}
At a boundary after 300 selected clauses in the DISCOUNT experiment,
\setting{packed_fast} took 10.23 user seconds, versus 27.72 for FPA and 50.02
for the first packed mode.  All modes produced the same byte-for-byte sequence
of hint matches and hint-state changes.

\subsection{Collective expansion}

The collective inference scheduler creates one small resume record for paramodulation from
a given clause, paramodulation into it, positive hyperresolution, and negative
hyperresolution.  Each record contains the parent clause numbers and the exact
position in the inference-rule iterator---the procedure that enumerates
possible conclusions one at a time---at which generation should continue.  It
also records which
clauses were active when the work was created, so later activations cannot be
used as if they had already been available.  A balanced scheduler gives some
turns to every enabled rule, stops creating records at an upper limit, resumes
after their count falls below a lower limit, and permits only a bounded number
of conclusions per turn.  Saving the iterator position avoids regenerating and
discarding the same prefix on every turn.

Optional look-ahead asks which member of a small bounded group would match a
hint, but uses the answer only for ordering.  It does not assign a clause number
or change a hint.  If a conclusion is processed early, its sequence number and
structural checksum identify the precise conclusion that the later normal scan
must skip.  Some turns continue in first-in, first-out order, ensuring that
every finite pending inference is eventually processed.

\subsection{Why it did not reproduce Osborn}

Some DISCOUNT/collective runs matched more hints than the historical proof but
did not prove within the tested resources.  A hint match says that a useful
clause shape appeared; it does not say that the same ancestors exist, the same
demodulators were available, or the clause survived in the same normal form.
Traditional OTTER admits an unselected SOS equation as a demodulator
immediately.  Selected DISCOUNT delays it.  Eager-interreduced DISCOUNT also
rewrites each demodulator with the other demodulators, keeping the rules
mutually simplified.  This stronger rewriting can remove shapes expected by
the historical chain.

The more eager DISCOUNT variants had to revisit old passive clauses whenever
the rewrite system changed.  At one stage the queue of clauses waiting to be
resimplified could consume every scheduler turn, leaving no turn for a
generating inference.  Limits on that queue and mandatory inference turns
restored progress, but did
not recover the old sequence of selected clauses.  The result illustrates a
familiar ATP fact: fairness or refutational completeness does not imply the same
proof under a finite resource limit.  Demodulation and inference scheduling are
part of the practical strategy.

\section{The accepted eager compact-OTTER architecture}

Phase 5 retains \setting{search_loop=otter} and
\setting{inference_frontier=clauses}.  Each retained candidate completes the
ordinary sequence of immediate simplification, hint matching, redundancy
tests, and index updates.  Afterwards its body is archived and long-lived
passive structures refer to it by clause number rather than by pointers to its
literals and terms.

\begin{lstlisting}
infer an ordinary candidate
  -> demodulate and simplify literals
  -> safe unit-conflict test
  -> exact hint matching and weighting
  -> resource limits, semantic tests, and keep/delete rules
  -> forward subsumption
  -> assign a stable clause number
  -> admit a demodulator when appropriate
  -> backward subsumption and backward demodulation
  -> update the four smaller passive-clause indexes
  -> serialize body and justification
  -> retain only the small selection record and clause numbers in RAM

select a given clause
  -> locate its archive record by stable number
  -> reconstruct the ordinary clause
  -> remove its entries from the passive-clause indexes
  -> activate the clause
  -> make ordinary inferences at the same stage as old OTTER
\end{lstlisting}

\subsection{File archive whose records are never overwritten}

With \setting{ancestor_store=file}, records are appended to a disk file and are
not modified in place.  A checksum detects accidental damage.  The
\setting{pread} and \setting{pwrite} system calls transfer only the requested
record through a small RAM buffer.  A record retains the compressed clause,
attributes, flags, hint state, and parent clause numbers.  The same archived
body serves passive processing and proof extraction; the selector keeps no
second collection of clause bodies.

The accepted proof's archive was 84,404,096 logical bytes and used one 4-KiB I/O
buffer.  It performed about 3.8 million reads totaling 374 MB and 412,000 writes
totaling 84.4 MB.  The 84.4-MB logical file length is a disk quantity, not
process RAM.  The operating system may retain recently read blocks in its
discardable filesystem cache, so cgroup accounting is needed for a total-job
measurement.

\subsection{Dense given-clause selection}

The small SOS records contain everything inspected by the given-clause
selection rules, but no literals or terms.  They preserve the alternating
low-weight/high-weight cycles, breadth-first level, semantic classification,
weight, matched hint, age, and queue membership.  At the final boundary 131,001
passives used 9,532,864 bytes of records and 611,368 bytes of priority queues.

The implementation can retain recently reconstructed passive clauses in RAM,
but the accepted cache size is zero.  Controlled 0, 4, and 32-MiB experiments
at 1500 givens avoided about 98,000 reconstructions without improving CPU;
nonzero caches increased RSS.  Examining too many index candidates, not archive
decoding, was the dominant cost.

\subsection{Four compact passive-clause indexes}

The compact rewrite-rule store holds encoded rule sides, rule kind, activity, and
the clause number needed for a proof.  A discrimination-tree-style index finds
possible rules.  Consecutive one-child steps are stored as one short sequence.
Additional lists map term features to clause numbers and positions that may be
rewritable by a new rule.  The new index only proposes rules; ordinary matching,
term ordering, and rewriting make the final decision.  It used 11,205,308 bytes
at the proof boundary.

The compact unit index finds possible generalizations, instances, unifiable
units, forward/backward unit-subsumption partners, and unit conflicts.  It
records compact term paths, clause-number lists, literal sign, and one yes/no
bit saying whether each symbol occurs.  A surviving unit is reconstructed for the ordinary exact
test.  The index used 13,166,960 bytes.

The backward-demodulation index must find matching subterms anywhere in a
clause.  It groups occurrences by root symbol, clause number, and nearby symbols
along the term path.  Because clause numbers and positions normally increase,
it stores each difference from the preceding number instead of repeating every
full number.  The ordinary matcher checks all survivors.  This index used
12,109,376 bytes.

The nonunit subsumption index stores standard numerical clause features, such
as literal counts and symbol occurrences, in a compact prefix tree.  Feature
sequences with the same beginning share the same initial tree path.  These
necessary conditions reject impossible partners; ordinary Prover9 subsumption
checks every survivor.  It used 1,508,576 bytes.

\subsection{Shared serialized terms}

The first versions copied the same clause-term encoding into several indexes.
The final version stores one sequence of 32-bit symbol and variable numbers per
clause.  The first index creates it and later indexes record the position of the
same sequence.  A two-level clause-number table allocates lookup space only for
ID ranges that are used.  When the token array fills, capacity grows by 12.5\%
rather than doubling a large allocation.

Deleted or replaced clauses leave unused sequences.  Periodically the live
sequences are copied together.  The code builds a table translating every old
position to its new position, rebuilds all four dependent indexes, and exposes
the new pool only when every reference agrees.  Large lists and translation
tables are sorted through a temporary file so that several large temporary arrays
do not coexist in RAM.  On Linux, \setting{mremap} can sometimes move the
virtual-memory mapping without copying the token bytes.

At the proof boundary the pool held 3,220,436 tokens in 16,219,320 bytes.  Five
rounds of packing live sequences together had recovered 14,793,444 bytes.  The
four indexes reused an already stored token 38,557,344 times rather than making
another copy.

Equal subterms from different clauses are not yet merged.  At 1000 givens there
were 728,510 subterm occurrences but only 91,686 structurally different terms.
A directed acyclic graph with one shared node per different term was
estimated at 1,304,344 bytes for bare term nodes and child references, compared
with 4,194,304 bytes then
reserved by the token pool.  A usable version would also need a lookup table,
information saying which nodes remain used, and spare capacity, so the actual
saving would be lower.

\subsection{Packed-fast hints}

The accepted hint collection combines compressed bodies with lists of hint numbers
sharing safe structural features.  For a query described by at most eight such
features, a fixed 16,384-entry cache can retain the exact combined list if it
also contains at most eight possible hints.  Wider queries or larger answers
recombine their lists in the ordinary way.  Each cache
entry is 136 bytes, so the table remains 2,228,224 bytes however long the search
runs.  The final hit rate was 35.08\%, avoiding examination of 136,373,547 hint
numbers from the individual feature lists.

Compression does not freeze logical hint state.  Rewritten hints receive new
index entries; version numbers identify obsolete entries until a rebuild removes
them.  Degradation and match-once state change only after ordinary exact
matching, and checkpoints save those changes.  Bodies, index lists, mutable
state, and cache together used about 15.2\mib for 88,494 hints.

\subsection{Controlling dead records and peak memory}

Small permanent records did not by themselves control peak RSS.  An index
rebuild can temporarily hold old and new representations together, and obsolete
entries can accumulate.  The final design therefore:
\begin{itemize}
  \item rebuilds an index when a configured percentage of records is obsolete;
  \item packs away unused term sequences after their estimated total reaches a
        configured threshold;
  \item reads only 4096 archived clause numbers at a time while rebuilding the
        backward-demodulation index;
  \item sorts large clause-number and old-to-new-position tables through a
        temporary file;
  \item frees an old array as soon as its information has been transferred,
        before allocating the next replacement array;
  \item reuses storage already allocated for compact records;
  \item uses small direct clause-number tables allocated only for occupied ID
        ranges instead of general per-entry hash tables;
  \item releases dense passives, hints, and compact search indexes before final
        proof-DAG expansion;
  \item with \setting{P9_COMPACT_HEAP=1}, asks the GNU C allocator to return
        freed medium-sized arrays promptly to the operating system.
\end{itemize}

These allocation and release rules prevent an index rebuild or final proof from
holding two large generations of data simultaneously.

\section{Correctness evidence}

\subsection{Side-by-side and focused tests}

The implementation was repeatedly checked against the old representation at
bounded search prefixes.  Focused tests cover damaged archive records, memory
allocation and release, and removal of deleted selection records.  They also
check adjustment of term positions when the shared pool is packed,

\subsection{General-indexing implementation and bounded gates}

The corrective plan has now been implemented on
\setting{general-compact-indexing}.  The product composition traverses the
existing shared compact term tree as a code tree for unit unification and
instance retrieval; rejects impossible nonunit subsumption candidates with
fixed rigid-path and repeated-variable summaries before archive
reconstruction; replaces the CHAT-shaped packed-hint cache with a complete
variable-length-key ring bounded by \setting{hint_cache_kb}; and rebuilds stale
hint postings from measured wasted scans as well as stored garbage.
High-frequency hint clocks use deterministic 1/64 sampling instead of two
resource-usage system calls per query.  Established exact routines remain
authoritative for every logical answer.

Several structurally stronger backward-demodulation prototypes were rejected
rather than fitted to Osborn.  A wider signature exceeded the 20\% byte gate at
300 givens.  A full exact code tree reduced 1000-given posting work by orders of
magnitude but grew the back index 57.44\% and slowed the run 4.77\%.  Length,
hot-root, and exact-position admission policies did not buy enough work
reduction per byte.  The candidate therefore retains the complete
\setting{mask8} fallback.

At the frozen 1000-given training gate, paired runs preserved all
given/generated/kept and rule counters on Osborn, the extracted 11,000-given
input, nil3, and generalized-Bol.  Nonunit exact tests changed from
74,374 to 5,167; 75,171 to 5,142; 9,478 to 812; and 9,265 to 827,
respectively.  Archive materializations on the two rewrite-heavy cases fell
from 56,286 to 1,255 and from 56,120 to 1,069.  Nonunit-index growth was 7.21\%
there and 1.35--1.43\% on the no-demodulation cases.  The worst CPU increase
was 2.72\%, and peak RSS changed by at most 128\,KiB.

Commit \setting{1319fbf} froze the candidate before the four declared holdouts
were opened.  At 300 givens all eight paired runs had identical logical
boundaries.  In aggregate, nonunit exact tests fell from 14,986 to 1,730
($-88.46\%$) and archive materializations from 2,123 to 706 ($-66.75\%$) for
0.79\% nonunit-index growth.  Candidate/control user-CPU geometric mean was
0.986, the worst increase was 5.18\%, and RSS differed by at most 128\,KiB.
No parameter was tuned from these results.  Commands, per-case tables, hashes,
option meanings, and the checked-in candidate configuration are in
\setting{benchmarks/compact-generalization/README.md}.

This closes the bounded implementation and short holdout phase, not the
radical production gate.  The 1000-given holdout tier and controlled
11,000-given, Osborn, AAPERM, and multi-million-passive runs remain for a
suitable host with cgroup accounting.

\subsection{Expected saving on very large AIM runs}

For problems where reproducing the old selected-clause order matters, compact
OTTER's accepted measurement is 76.85\%
less peak RSS.  The fixed 88,494-hint collection and 131,001-clause final SOS make a
literal 80\% difficult on this particular proof.  The obsolete run and current
11,000-given rerun show that savings can grow when millions of passive clauses
and their indexes dominate.  The current run reports 76.84\% less peak RSS.  It
should not be extrapolated quantitatively because it uses a different input
profile, had allocator compact policy disabled, and has no cgroup accounting
for cached file data.

For bounded collective DISCOUNT the intended large-search behavior is stronger:

\begin{lstlisting}
ordinary OTTER RAM
  = fixed hints
    + memory growing with every passive body and eager index entry
    + proof history

DISCOUNT/collective RAM
  = packed hints
    + memory growing with selected active clauses and indexes
    + compact parent history and resume records
    + a fixed configured number of pending conclusions
    + file-backed bodies
\end{lstlisting}

Replacing 4.59 or 8.50 million complete in-memory SOS clauses by the smaller
active set, compact proof history, resume records, and a fixed-size group of
conclusions makes an 80--95\% whole-process reduction plausible.  The 90\%
midpoint is only a planning estimate, not an accepted measurement.

The defensible statements are:
\begin{itemize}
  \item accepted: 76.85\% lower external peak RSS at the same proof boundary
        without CPU penalty;
  \item current large-profile diagnosis: at 11,000 givens, 76.84\% lower
        self-reported peak RSS and 89.82\% lower internally accounted memory,
        but 2.388 times the CPU, allocator compact policy disabled, and no
        cgroup page-cache accounting;
  \item conditional forecast: 80--95\% less total RAM on much larger
        AIM searches with millions of passive clauses, awaiting current-binary
        RSS/PSS,
        cgroup page-cache, and proof/coverage experiments.
\end{itemize}

\subsection{Bounded progression}

On a low-memory or slow host, begin with 100--300 givens and a deterministic
hint sample, then all hints at 300, 1000 givens, a time-bounded 2000--4000
prefix, and only then a full run.  Keep limits both inside Prover9 and in the
invoking shell.  Independent small runs may use separate real cores if the sum
of their expected peak RSS fits in physical memory.  A hint sample is useful
for debugging and side-by-side prefix comparisons, not as a proof replacement.

\subsection{Archive location and measurement}

Current source creates both archive files in \setting{TMPDIR}, using
\setting{/tmp} only when the variable is unset or empty.  An explicitly bad
directory is an initialization error rather than a silent fallback.  The
\setting{prover9-ancestors-XXXXXX} and
\setting{prover9-passive-XXXXXX} files are unlinked immediately.  Unlinking
removes the directory name but not the contents while Prover9 holds the file
open.  The files are visible through \setting{/proc/PID/fd} and disappear on
exit or forced termination.

Logical size, allocated blocks, and residency can be inspected with
\setting{readlink}, \setting{stat -L}, \setting{du -hL}, and
\setting{/proc/PID/smaps}.  The last applies to an mmap backend; the recommended
explicit-file backend has no whole-file mapping, so charged file cache must be
read from the cgroup.  A long run can use, for example,
\setting{TMPDIR=/local/p9-archive}.

When claiming total job RAM rather than process RSS, also record cgroup-v2
\setting{memory.peak} and the file-cache fields in \setting{memory.stat}.

For each comparison report proof/stopping reason; all main clause populations;
proof length and \setting{prooftrans} result; user/system/wall time; external
maximum RSS; RSS/PSS at common given boundaries; archive logical bytes
separately; and compact-index bytes, exact tests, rebuilds, and validation
failures.  Do not use only the last active-hint \setting{matched=} value: in
some reports it counts only hints active at that moment, not all earlier matches
or cumulative proof progress.  The cumulative \setting{Generated} count is
also insufficient because it includes immediately rejected clauses.

\section{Future work}

\subsection{Replace broad compact retrieval with selective indexes}

The current-binary \setting{chat_test.new.out3} run supplies the previously
missing large-profile result.  It preserves the compact run's terminal search
and lowers the embedded peak-RSS diagnostic by 76.84\%, but remains 2.388 times
slower than ordinary Prover9.  Parameter tuning is not an adequate response:
unit conflict and backward demodulation still traverse 19.190 billion exact
candidates and 21.500 billion posting groups, respectively.

That phased implementation is complete through the four-category 1000-given
training gate and untouched 300-given holdout prefixes.  Selective unit
retrieval, nonunit pre-materialization rejection, byte-bounded general hint
caching, stale-work maintenance, and lower-overhead clocks passed.  Several
backward-demodulation replacements failed their byte/work gates and remain
diagnostic.  The candidate stays explicit until the long gates pass.  Next
compare ordinary indexes/full bodies, compact indexes/full bodies, and complete
file-backed mode with \setting{P9_COMPACT_HEAP=1}, external RSS/PSS, and cgroup
page-cache accounting.

\subsection{Multi-million-SOS validation}

Run current compact OTTER and DISCOUNT/collective on several problems with
millions of passive clauses,
problems including Osborn and AAPERM, with identical hashes and limits.  Report
memory and CPU after equal numbers of selected clauses.  Also report how many
problems each mode solves under equal time and memory limits, because different
search paths can do unequal logical work at the same given count.  A radical
claim should require at least 80\% lower external peak RSS,
corresponding cgroup whole-job/page-cache measurements, and at least 95\% PSS
accounting.

\subsection{Reduce false candidates reaching exact tests}

Future indexes should report how often a query returns 0, 1, a few, or a very
large number of possible answers; average bytes per node hide rare catastrophic
queries.  Options include recording deeper term positions only when measured
rarity makes them selective; standard substitution-tree or code-tree indexes
that prune while performing matching or unification; compressed blocks of
clause numbers with markers that let intersection skip an irrelevant block;
separate unit indexes for different operations; and more exact matching on the
compact number sequence.  Every prototype must reproduce the complete
300-given event log and be compared with the final index, not the first packed
version.

\subsection{True cross-clause term sharing}

At 1000 givens, 87.4\% of subterm occurrences duplicated a term found elsewhere.
This justifies a shared term DAG with one node for each structurally different
term, often called hash-consing.  The nodes cannot change after creation.  Such
a design needs a construction table that finds an equal existing node,
information saying which nodes remain
used, matching and rewriting over shared node numbers, an archive format
independent of process-local numbers, and a peak analysis while old and new
DAGs coexist.  The current count gives only the maximum plausible saving; the
lookup table and used-node information may consume much of it.

\subsection{Move old feature lists to disk}

Compact OTTER still keeps in RAM the indexes that must return every possible
passive-clause candidate.  A two-level design could keep a small directory and
recent entries in RAM while placing compressed, read-only blocks of clause
numbers on disk.  Block summaries would let list intersection skip irrelevant
blocks, and occasional large sequential merges would remove obsolete entries.
Backward demodulation is difficult because one rule can require a broad search;
batching several new rules and scanning blocks sequentially may beat millions
of small reads.

\subsection{Direct compact rewriting}

A direct compact rewriter could read a clause's number sequence into one
fixed-size work area, rewrite it, and emit a replacement archive record without
constructing a full \setting{Topform} and term tree.  It must preserve
justifications, attributes, hints, orientation, and action side effects, and
should measure backward-demodulation/preprocessing time and temporary RSS.

\subsection{Collective proof guidance}

Collective search should favor construction of connected parts of a proof, not
merely many unrelated hint shapes.  Signals might ask whether a candidate
completes the known parent requirements of a later hint, how many known proof
steps lead to a not-yet-matched successor, which inference rules and directions
occur in source proofs, and whether the expected normal form is preserved.
Some turns must still process pending work in creation order, and every
previewed conclusion must undergo ordinary exact clause processing once.

\subsection{Two-stage workflow and operational hardening}

Where the exact sequence of selected clauses is not required, many low-memory
DISCOUNT/collective
jobs can discover proofs or hints, followed by a smaller number of compact-
OTTER proof-producing reruns.  Evaluate solved problems per machine-day and
verified proofs per GiB.

Operational work should check free space and expose the resolved archive
directory and open-file number directly (the stores now honor
\setting{TMPDIR}),
collect cgroup-v2
counters, record hashes and external time automatically, test the required RSS
upper limit across platforms, and publish option incompatibilities.

\section{Conclusion}

Millions of SOS clauses were not merely proof debris.  Under the OTTER loop
they remained active for contraction and therefore occurred in several term
and clause indexes.  Hints and proof ancestors added fixed and historical
costs.  Radical memory reduction required changing ownership across the whole
saturation state rather than deleting one list.

The DISCOUNT/collective architecture gives the best bound on how RAM grows with
the search and remains promising for exploration with very large passive sets.
It also showed that the practical behavior of an ATP is not determined by
inference rules alone.  The timing of demodulation, normalization, hint
matching, and rule interleaving can decide whether a known proof is found.

Compact OTTER resolves that tension for the current problem, where reproducing
the old selected-clause sequence matters.  It preserves the order of immediate
simplification and hint operations.  Complete passive clauses move to an exact
disk archive, and smaller indexes refer to them by clause number rather than
pointer.  The indexes propose possible answers and the old exact routines still
decide them.  It proves at the same 2945-given boundary with 76.85\% less peak
RSS and no CPU penalty on that acceptance case.  The larger 11,000-given run
shows that this CPU conclusion does not generalize: current compact OTTER is
2.388 times slower there despite a 76.84\% lower embedded peak-RSS diagnostic.

The literal 80--90\% target is not yet a universal measured claim.  The
accepted proof saves 76.85\%; the current large-profile run reports 76.84\%
but is too slow, used no compact allocator policy, and did not charge the
cgroup's cached file data.  The general-purpose indexing candidate now passes
its frozen 1000-given training and 300-given short-holdout gates without
post-hoc tuning.  The next decisive evidence is the remaining 1000-given
holdout tier followed by controlled 11,000-given and multi-million-SOS AIM
runs.
